# OrcaSVN Windows 性能排查 · 2026-11-25

测试基线为 `b883e03` 加工作区原有的自动二进制冲突处理改动。使用 Windows、SVN 1.14.5 和 Rust Debug 测试二进制。真实工作副本只执行本地状态与元数据查询。冲突写入用例使用独立 `file://` 仓库。

## 状态刷新

- CLI 三轮普通 `svn status --xml` 耗时 13.95–16.98 秒，返回 777 条状态。Verbose 查询包含约 12.1 万个正常条目。原生全文件清单约 25.6 万项，单独遍历测到 11.83–15.45 秒。
- 当前权限访问 USN 返回 Windows 错误 5，程序改用目录通知。旧版把所有目录通知都视为结构变化。一次打开或手动刷新即使已拿到有效 SVN 结果，也会因目录通知丢弃并行建立的缓存。紧接的轮询再串行枚举文件清单和运行 SVN，4 次均重新全量扫描，耗时 26.10–31.76 秒。
- 监听探针观察到 SVN 忽略目录内部仍有写入。单独过滤这些目录的后代后，旧的目录元数据处理仍触发重扫，两次轮询用了 25.11 和 28.31 秒。Windows 通知解析因此保留新增、删除、重命名与普通修改的区别。已有普通目录的属性或时间戳变化无需重扫，目录本身的增删和移名、重解析点、SVN 管理数据和配置变化仍走原有核验。
- 最终版使用 SVN 自己返回的忽略项建立监听过滤范围，完整查询仍返回原有可见状态。真实工作副本两次轮询均耗时 3.4 毫秒，启动 0 个 SVN 子进程，结果逐项与权威查询一致。打开和手动刷新仍执行完整 SVN 查询，该轮分别为 18.58 和 19.33 秒。
- 手动或写操作后的强制查询遇到已持有缓存锁的旧扫描，直接启动新的权威查询并使旧基线失效。隔离用例持有旧锁时仍能取到最新文件状态。

## 自动二进制冲突

- 真实工作副本本轮观察到 61 个 `Binaries` 冲突。旧路径在工具栏保持忙碌的同时按文件调用 Tauri。每个文件重复查询工作副本身份、文件所有者、MIME 和状态，每次回填还会重新处理前端状态列表。
- 同一隔离用例给定 8 个路径、自动处理 5 项，旧版耗时 7.79 秒和 104 次 SVN 调用。新版耗时 1.63 秒和 20 次 SVN 调用。计时覆盖后端批次，排除夹具创建和前端渲染。
- 每批最多 8 个路径，共用工作副本锁、身份校验和定向状态查询。每个文件仍检查工作副本所有权和二进制类型，写入前保存可恢复备份。前端每批合并一次状态，在批次之间释放操作锁。失败和不适用路径在相同工作区代次内不会因普通轮询而反复尝试。
- 用例核对内容、属性冲突和文件级树冲突。自动处理前后的工作文件字节以及本地属性一致，文本和其他目录的资源冲突仍留在列表中。

## 暂存包

导入和导出需要验证哈希、复制文件和刷盘。旧版 Tauri 同步命令在 IPC 处理线程执行这些 I/O。新版在阻塞任务池中执行，导入、删除和迁移完成后只刷新暂存列表。前端测试验证这三条路径都跳过工作副本扫描。本轮未测真实大型暂存包的桌面交互耗时。

## 复测

在能运行 `svn` 和 `svnadmin` 的目录执行以下命令。工作副本路径应选择本地测试副本。状态基准在每轮比较完整状态，期间实际变更状态会让这轮失败。

```powershell
$env:ORCASVN_BENCH_WORKSPACE = '<本地 SVN 工作副本>'
cargo test --manifest-path src-tauri/Cargo.toml benchmark_workspace_refresh -- --ignored --nocapture
cargo test --manifest-path src-tauri/Cargo.toml automatic_binaries_resolution_keeps_bytes -- --nocapture
npm run test:unit
```

原生测量未计入桌面启动、IPC、渲染与服务器响应。实际工作副本的自动解决、远端更新和提交未在现场执行。
